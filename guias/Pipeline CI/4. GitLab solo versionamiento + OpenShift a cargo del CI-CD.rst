Introducción
============

Este manual describe cómo configurar GitLab como mero repositorio de código
y delegar la totalidad del ciclo CI/CD a OpenShift mediante Pipelines as
Code (PaC), basado en Tekton.

Al operar tu instancia de GitLab local sobre HTTP (sin certificado SSL) en
conjunto con OpenShift Local (CRC), esta guía incluye la habilitación de
peticiones locales en GitLab, la instalación del operador de Tekton, los
ajustes específicos de red, la creación de namespaces, permisos de
ServiceAccount y parámetros de Buildah necesarios para evitar bloqueos de
comunicación o fallos de almacenamiento en contenedores sin privilegios.

Paso 0: Habilitar Webhooks locales en GitLab (Requisito crítico)
================================================================

Por defecto, GitLab bloquea las peticiones de Webhooks hacia direcciones IP
privadas o dominios locales como ``apps-crc.testing`` por políticas de
seguridad (SSRF). Debes habilitarlo antes de empezar:

1. Inicia sesión en tu GitLab con cuenta de Administrador.
2. Ve a **Admin Area** (icono de llave inglesa) → **Settings** → **Network**.
3. Expande la sección **Outbound requests**.
4. Marca la casilla **Allow requests to the local network from webhooks and
   integrations**.
5. Haz clic en **Save changes**.

Paso 1: Desactivar el CI/CD nativo de GitLab
============================================

Para evitar ejecuciones duplicadas o conflictos, desactiva el motor CI/CD
de GitLab en tu proyecto:

1. Entra a tu proyecto en GitLab.
2. En el menú lateral ve a **Settings** → **General**.
3. Expande **Visibility, project features, permissions**.
4. En la sección **Repository**, desactiva el interruptor **CI/CD**.
5. Haz clic en **Save changes**.

Paso 2: Instalar y habilitar OpenShift Pipelines (Tekton) y PaC
===============================================================

En instalaciones limpias de OpenShift Local (CRC), el operador de Tekton no
viene preinstalado. Sigue estos pasos como administrador del clúster
(``kubeadmin``):

1. Verificar si el operador ya existe:

   .. code-block:: bash

      oc get pods -n openshift-pipelines | grep pipelines-as-code

   Si devuelve ``No resources found in openshift-pipelines namespace``,
   procede con la instalación.

2. Crear la suscripción para instalar el operador oficial de Red Hat:

   .. code-block:: bash

      cat <<EOF | oc apply -f -
      apiVersion: operators.coreos.com/v1alpha1
      kind: Subscription
      metadata:
        name: openshift-pipelines-operator-rh
        namespace: openshift-operators
      spec:
        channel: latest
        installPlanApproval: Automatic
        name: openshift-pipelines-operator-rh
        source: redhat-operators
        sourceNamespace: openshift-marketplace
      EOF

3. Monitorear el despliegue de los componentes:

   .. code-block:: bash

      watch "oc get pods -n openshift-pipelines"

   Espera unos minutos hasta que los pods principales
   (``tekton-pipelines-controller``, ``tekton-triggers-controller``,
   ``tekton-events-controller``) aparezcan en estado ``Running``. Presiona
   ``Ctrl+C`` para salir del monitoreo.

4. Asegurar la activación del controlador Pipelines as Code en
   ``TektonConfig``:

   .. code-block:: bash

      oc patch tektonconfig config --type=merge -p='{"spec":{"platforms":{"openshift":{"pipelinesAsCode":{"enable":true}}}}}'

5. Verifica que el pod ``pipelines-as-code-controller-xxxx`` levante en
   estado ``Running``:

   .. code-block:: bash

      oc get pods -n openshift-pipelines | grep pipelines-as-code

Paso 3: Crear el Namespace y configurar ServiceAccounts en OpenShift
====================================================================

1. Crear el proyecto (namespace) en OpenShift:

   .. code-block:: bash

      oc new-project my-app-dev

   .. note::

      Si prefieres usar el proyecto ``demo-app`` que ya tienes creado,
      simplemente reemplaza ``my-app-dev`` por ``demo-app`` en los
      comandos siguientes.

2. Configurar el ServiceAccount y los permisos. Una vez creado el
   proyecto, aplica los comandos para configurar el ServiceAccount de
   despliegue y el de Tekton:

   .. code-block:: bash

      # Cambiar al proyecto
      oc project my-app-dev

      # Crear el ServiceAccount dedicado para GitLab/Deployer
      oc create sa gitlab-deployer-sa

      # Dar permisos de edición al ServiceAccount deployer
      oc policy add-role-to-user edit -z gitlab-deployer-sa -n my-app-dev

      # Dar permisos de edición al ServiceAccount predeterminado de Tekton ('pipeline')
      oc policy add-role-to-user edit -z pipeline -n my-app-dev

      # Dar permisos de Lectura al ServiceAccount predeterminado de Tekton ('pipeline')
      oc policy add-role-to-user view -z pipeline -n my-app-dev

Paso 4: Obtener la URL del controlador de PaC
=============================================

Obtén la ruta pública de OpenShift hacia donde GitLab enviará los eventos:

.. code-block:: bash

   echo https://$(oc get route -n openshift-pipelines pipelines-as-code-controller -o jsonpath='{.spec.host}')

El resultado tendrá un formato similar a:
``https://pipelines-as-code-controller-openshift-pipelines.apps-crc.testing``

Paso 5: Crear un Personal Access Token en GitLab
================================================

PaC necesita un token para leer el código fuente y reportar el estado del
pipeline (checks) de vuelta en tus commits de GitLab:

1. En GitLab ve a **User Settings** → **Access Tokens**.
2. Crea un token con los siguientes scopes:

   - ``api`` (obligatorio)
   - ``admin:repo_hook`` (necesario para configurar el Webhook
     automáticamente)

3. Copia y guarda el token generado.

Paso 6: Configurar el Repository CR y el Webhook
================================================

Opción A: Automático mediante la CLI tkn pac (Recomendado)
----------------------------------------------------------

Ejecuta el asistente en la raíz de tu repositorio local:

.. code-block:: bash

   tkn pac create repo

Completa los datos solicitados asegurándote de usar ``http://``:

- **URL del repositorio**: ``http://tu-gitlab.local/tu-usuario/tu-repo.git``
- **Namespace de OpenShift**: ``my-app-dev``
- **Project ID de GitLab**: el número identificador visible en la página
  principal de tu proyecto.
- **URL del controlador PaC**: confirma la detectada en el Paso 4.
- **Secret del Webhook**: acepta el valor generado por defecto.
- **GitLab API URL**: ``http://tu-gitlab.local`` (nota: usar HTTP, no
  HTTPS).

Opción B: Configuración Manual (Control total)
----------------------------------------------

Si prefieres aplicar los manifiestos directamente en OpenShift:

.. code-block:: bash

   # 1. Crear el Secret con el token de GitLab y el secreto del Webhook
   oc -n my-app-dev create secret generic gitlab-webhook-config \
     --from-literal provider.token="<TU_PERSONAL_ACCESS_TOKEN>" \
     --from-literal webhook.secret="<WEBHOOK_SECRET>"

   # 2. Crear el recurso Repository apuntando a HTTP
   cat <<EOF | oc apply -f -
   apiVersion: "pipelinesascode.tekton.dev/v1alpha1"
   kind: Repository
   metadata:
     name: my-app-repo
     namespace: my-app-dev
   spec:
     url: "http://tu-gitlab.local/tu-usuario/tu-repo.git"
     git_provider:
       type: "gitlab"
       url: "http://tu-gitlab.local"
       secret:
         name: "gitlab-webhook-config"
         key: "provider.token"
       webhook_secret:
         name: "gitlab-webhook-config"
         key: "webhook.secret"
   EOF

.. warning::

   Si configuras el Webhook manualmente en GitLab (**Settings** →
   **Webhooks**), pega la URL del Paso 4, ingresa tu ``WEBHOOK_SECRET``,
   selecciona **Push events** y **Merge request events**, y **desmarca**
   la casilla **Enable SSL verification** ya que CRC utiliza certificados
   locales autofirmados.

Paso 7: Crear el archivo .tekton/pipelinerun.yaml blindado
==========================================================

Crea la carpeta ``.tekton`` en la raíz de tu repositorio y dentro crea el
archivo ``pipelinerun.yaml``.

Este manifiesto ya incluye:

- La variable nativa ``{{ revision }}`` de PaC para etiquetar la imagen con
  el SHA del commit.
- Parámetros de buildah adaptados para contenedores sin privilegios en CRC
  (``--storage-driver=vfs`` y ``--tls-verify=false``).
- Push directo al servicio interno del registry
  (``image-registry.openshift-image-registry.svc:5000``).
- Separación explícita entre el nombre del Deployment y el nombre del
  Container.
- Validación estricta post-despliegue que marca el pipeline como fallido
  si la imagen no se actualiza correctamente.

.. code-block:: yaml

   apiVersion: tekton.dev/v1beta1
   kind: PipelineRun
   metadata:
     name: "my-app-pipeline-run"
     annotations:
       pipelinesascode.tekton.dev/on-event: "[push]"
       pipelinesascode.tekton.dev/on-target-branch: "[main]"
       pipelinesascode.tekton.dev/max-keep-runs: "5"
   spec:
     params:
       - name: repo-url
         value: "{{ repo_url }}"
       - name: revision
         value: "{{ revision }}"
       - name: deployment-name
         value: "my-app-simple-dev"
       - name: container-name
         value: "my-app-simple-dev"
       - name: namespace
         value: "my-app-dev"
     workspaces:
       - name: source
         volumeClaimTemplate:
           spec:
             accessModes:
               - ReadWriteOnce
             resources:
               requests:
                 storage: 1Gi
     pipelineSpec:
       params:
         - name: repo-url
         - name: revision
         - name: deployment-name
         - name: container-name
         - name: namespace
       workspaces:
         - name: source
       tasks:
         - name: clone-build-push
           workspaces:
             - name: source
               workspace: source
           taskSpec:
             workspaces:
               - name: source
             steps:
               - name: git-clone
                 image: alpine/git:latest
                 workingDir: $(workspaces.source.path)
                 script: |
                   git clone $(params.repo-url) .
                   git checkout $(params.revision)

               - name: build-and-push
                 image: quay.io/buildah/stable:latest
                 workingDir: $(workspaces.source.path)
                 script: |
                   IMAGE_URI="image-registry.openshift-image-registry.svc:5000/$(params.namespace)/$(params.deployment-name):$(params.revision)"
                   echo "Construyendo imagen: $IMAGE_URI"
                   buildah bud --storage-driver=vfs --tls-verify=false -t "$IMAGE_URI" .
                   echo "Subiendo imagen al registry interno de OpenShift..."
                   buildah push --storage-driver=vfs --tls-verify=false "$IMAGE_URI"

         - name: deploy-and-verify
           runAfter:
             - clone-build-push
           taskSpec:
             steps:
               - name: oc-deploy
                 image: quay.io/openshift/origin-cli:latest
                 script: |
                   IMAGE_URI="image-registry.openshift-image-registry.svc:5000/$(params.namespace)/$(params.deployment-name):$(params.revision)"
                   echo "Actualizando deployment $(params.deployment-name)..."
                   oc set image deployment/$(params.deployment-name) $(params.container-name)="$IMAGE_URI" -n $(params.namespace)

                   echo "Esperando finalización del rollout..."
                   oc rollout status deployment/$(params.deployment-name) -n $(params.namespace) --timeout=300s

                   echo "Verificando integridad de la imagen desplegada..."
                   ACTIVE_IMAGE=$(oc get deployment $(params.deployment-name) -n $(params.namespace) -o jsonpath='{.spec.template.spec.containers[0].image}')
                   echo "Imagen activa -> $ACTIVE_IMAGE"

                   if [[ "$ACTIVE_IMAGE" != *"$(params.revision)"* ]]; then
                     echo "ERROR CRÍTICO: La imagen activa no coincide con el commit $(params.revision)."
                     exit 1
                   fi
                   echo "¡Despliegue verificado exitosamente!"

Paso 8: Ejecutar prueba y verificar logs
=======================================

Sube el archivo ``.tekton/pipelinerun.yaml`` a la rama ``main`` de tu
repositorio:

.. code-block:: bash

   git add .tekton/pipelinerun.yaml
   git commit -m "ci: configurar Pipelines as Code en OpenShift"
   git push origin main

Monitorea la ejecución directamente en OpenShift:

.. code-block:: bash

   tkn pipelinerun list -n my-app-dev
   tkn pipelinerun logs -n my-app-dev --last -f

Si el pipeline no arranca, revisa los logs del controlador de PaC:

.. code-block:: bash

   oc logs -n openshift-pipelines -l app=pipelines-as-code-controller --tail=100

Paso 9: Retirar el GitLab Runner antiguo
========================================

Una vez verificado que el flujo completo (Push → Webhook → Buildah →
Registry Interno → Rollout) funciona de principio a fin, puedes detener y
eliminar tu antiguo GitLab Runner. GitLab quedará operando exclusivamente
como servidor Git ligero.

Checklist de validación final
=============================

.. list-table::
   :header-rows: 1
   :widths: 60 40

   * - Requisito
     - Verificación
   * - Webhooks a red local habilitados en GitLab
     - Admin Area → Settings → Network → Outbound requests
   * - CI/CD nativo desactivado en el proyecto GitLab
     - Settings → General → Repository
   * - Operador OpenShift Pipelines y PaC activos
     - ``oc get pods -n openshift-pipelines``
   * - Namespace y roles creados (my-app-dev)
     - ``oc project my-app-dev``
   * - Rol edit asignado al ServiceAccount pipeline
     - ``oc policy add-role-to-user edit -z pipeline``
   * - ``git_provider.url`` en Repository CR usa HTTP
     - ``oc get repository -n my-app-dev -o yaml``
   * - Webhook en GitLab tiene SSL verification desmarcado
     - Settings → Webhooks
   * - ``.tekton/pipelinerun.yaml`` usa ``--storage-driver=vfs``
     - Validado en paso build-and-push
